## 3. BASE/DEEP 实际负载开销（30s 实测，proc_overhead + bpf_stats）

| 阶段 | 采集器自开销（单核占比） | BPF 程序内核总成本 | 主要开销来源（ns/s） |
|---|---|---|---|
| BASE | **49.3%** | snapshotter 2.34e9、on_sys_exit 1.62e9、on_sys_enter 1.29e9、task_iter 4.0e8、on_switch 3.3e8、fault_ret 2.2e8 | 64 核 per-CPU 采样器每 100ms 遍历 36 个 target 是最大项 |
| DEEP | **50.5%** | snapshotter 2.55e9、on_sys_exit 1.07e9、on_sys_enter 1.0e9、task_iter 4.3e8、on_switch 3.3e8、net_sock_state 1.0e8、net_softirq_exit 8.7e7 | 20ms 快采样 + DEEP syscall 对 + 网络 tp_btf 钩子 |

- BASE 与 DEEP 的自开销相近（约 50% 单核，即 64 核机器的 <1% 总容量），DEEP 增量主要来自 syscall 对与网络钩子。
- 64 核 per-CPU 采样器模式（5.15 无 `bpf_map_lookup_percpu_elem`）在 36 target 下产生约 115k 记录/s，因此 DrainPost 改为每个主循环（~10ms）drain，验证 0 overrun。

## 4. 各阶段插桩方式与采集频率

### 4.1 常驻（BASE，启动即 attach，从不重挂）
| 插桩点 | 方式 | 采集内容 | 频率 |
|---|---|---|---|
| `sched_switch` | tp_btf | target 的 on-CPU 时长/自愿·非自愿切换（target-gated）；DEEP 分支含 runq 延迟与无栈 off-CPU 降级 | 每次切换（仅 target 计入） |
| `sched_wakeup(_new)` | tp_btf | target 唤醒时间戳（BPF_NOEXIST 保留最早） | 每次唤醒（deep_mode + target） |
| `block_rq_insert/issue/complete` | tp_btf | 块 I/O 请求配对：每 tid/每设备 ops/bytes/latency hist13 | 每次完成 |
| `handle_mm_fault` | kretprobe | target minor/major 缺页计数（target-gated） | 每次返回 |
| `mm_vmscan_*` / `mark_victim` | tp_btf | 内存压力事件 / OOM 环 | 事件驱动 |
| 锁竞争（`contention_begin/end`，<6.0 退化为 `__mutex_lock_slowpath` kprobe） | tp_btf/kprobe | 锁等待计数/时长（per-tid + 全局 lock_hot） | 事件驱动 |
| `iter/task` | BPF_TRACE_ITER | 全任务表（pid/tgid/utime/…/min_flt/maj_flt） | **每 host tick 一次**（1s），全表复用给 selector/features/top-k |
| 飞行记录器 `snapshotter` | >=6.4 bpf_timer；5.15 每核 PERF_COUNT_SW_CPU_CLOCK | target 累计计数快照入 32768 槽环形区 | BASE **100ms**（fine_interval_ms）/ DEEP **20ms**（deep_fine_interval_ms） |

### 4.4 数据压缩策略（飞行记录器高效性核心）
- **批量累积**：内核只做 `PERCPU` 计数器原地递增（每事件 1 次 map 自增），不逐事件出队；用户态按周期一次读全量计数器。
- **全 eBPF 细粒度进程证据**：deep_proc 的 RSS 拆分/swap/ioac/schedstat 全部来自 `iter/task` 一次迭代，不再按 target 逐个读 `/proc/<tid>/status|io|schedstat`。
- **环形区批量上传**：快照按 target×tick 写入 seqlock 环形区，用户态 drain 后批量事务（BEGIN IMMEDIATE）落 SQLite，单次 drain 数千行只提交一次。
- **有损压缩（直方图）**：块 I/O/锁/syscall/futex/runq/文件 I/O 的时延分布只存 13-bin base-4 log2 直方图（syscall 64-bin），不逐样本存原始时延。
- **无损压缩（列存+增量）**：累计计数原始值存库，rate/百分比/分位数在消费端按相邻时间差与直方图计算，不重复落盘派生值。

## 5. 批量上传 vs 周期高频上传 + 压缩 负载/效率对比

基准：同一 `tp_btf/sched_switch` 挂点，各跑 15s。
- **批量累积（飞行记录器模式）**：PERCPU 计数自增，用户态 1 次 map 读取。
- **逐事件上传（高频模式）**：ringbuf 每事件 16B submit，用户态持续 poll+drain。

| 模式 | 事件速率 | 内核程序耗时（15s） | 用户态耗时（15s） | 单事件内核开销 | 单事件用户态开销 |
|---|---|---|---|---|---|
| 批量累积 | 97,623/s | 107.7 ms | **0.2 ms** | 73.5 ns | **0.1 ns** |
| 逐事件上传 | 631,062/s | 2137.8 ms | 8662.7 ms | 225.9 ns | 915.1 ns |

结论（按单事件归一）：逐事件上传内核成本约 **3.1×**，用户态成本高约 **4 个数量级**（915ns vs 0.1ns/事件）。批量累积几乎不产生用户态事件处理开销；再叠加直方图有损压缩（时延分布从逐样本 8B 降到固定 52/256B）与增量列存，飞行记录器在 115k 记录/s 的产生速率下仍能 0 overrun 落库。

对比图：**`docs/batch-vs-stream.svg`**（批量 vs 逐事件的单事件内核/用户态开销条形图，报告内附路径，可在浏览器直接打开）。

## 7. 因果推断证据的广度与深度（诚实评估）

DEEP 期证据按"干预→影响→后果"链路覆盖六维：CPU/调度（on-CPU 折叠栈、runq p50/p99、schedstat 三值、futex 直方图）；内存（缺页、锁热点、vmscan 事件、cgroup PSI）；块 I/O（每文件/每设备字节+时延 hist13）；网络（连接生命周期、drop reason、softirq 直方图）；GPU（进程级 SM/显存/编码器，100ms）；进程画像（RSS 四分量+swap+ioac+schedstat，1s，全 eBPF）。

**足够性**：作为相关性/根因定位证据充分——同一时间轴、同一 target 集、多层时延直方图能回答"谁、何时、哪类资源、多久"。严格反事实因果仍受三处限制（如实声明）：①无对照组/干预注入机制，因果模型拿到的是观测性 bundle；②5.15 降级项（fentry 全路径→dev/ino、off-CPU 栈→无栈 dwell、TCP RTT→重传证据，tcp_probe 已确认存在未接入）不静默归零但精度低于 6.6；③用户态函数级归因仅 on-CPU 栈。
